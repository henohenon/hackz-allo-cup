# 文字コードコーデック 設計メモ（思想・判断の根拠）

ユーティリティ側の **文字コード生成 → encode/decode** をなぜこの形にするか、の記録。
BLE 通信そのものの設計は [communication-design.md](./communication-design.md)（現行の正典）を参照。
旧モックの検証経緯（macOS 制約など）は [\_archive/docs](../../_archive/docs/)。

## 目的

> 何かしらの文字列/byte 列（= seed）から決定的にテーブルを生成し、
> **その seed を共有した者だけが復号できる**換字コーデックを整備する。

- 同じ seed なら両端でまったく同じテーブルが再現される（決定的）。
- seed を持たない者は、パケットを傍受してもテーブルを組み立てられない。
- アソビ枠なので「ガラパゴスな独自符号」を作ること自体が目的の一部。

> [!WARNING]
> これは**暗号ではない**。換字 + 小さな鍵空間なので解析には耐えない。
> 「共有者だけが読める雰囲気」「毎回見た目が変わる」を作る**難読化・遊び**であって、
> 秘匿性を担保する用途には使わない。

## 全体構造（三層）

```
  文字セット定義 ─┐
                 ├─→ テーブル生成( seed → 決定的PRNG → 全単射 ) ─→ encode / decode
  seed ──────────┘
```

肝は **「決定的 PRNG」と「自然乱数」を混ぜないこと**。役割が真逆：

| 種類            | 役割                             | 性質                                  |
| --------------- | -------------------------------- | ------------------------------------- |
| **決定的 PRNG** | seed からテーブルを組む          | 同じ入力 → 必ず同じ出力（再現性が命） |
| **自然乱数**    | セッションごとの seed の素を作る | 毎回違う（再現してはいけない）        |

`Math.random()` のような自然乱数でテーブルを組むと両端で並びがズレて復号不能になる。
テーブル生成に使うのは **seed 入りの再現可能 PRNG**。

## 主要な設計判断

### 判断1: seed を「事前共有鍵 + セッションID」の 2 層に分ける

「共有者だけ復号」と「毎回見た目が変わる」を両立させるため。

```
table = PRNG( 事前共有鍵  ++  セッションID )
                 ↑                ↑
        チームだけが持つ      自然乱数で毎回生成・パケットで平文送信(4Byte)
        （これが「共有」の正体）   （salt。同じ文でも毎回違うコードになる）
```

- **事前共有鍵**: アプリに焼く / 合言葉。これを持つ者だけがテーブルを再構築できる
  → 「共有された者だけ復号」の実体。
- **セッションID(4Byte)**: 自然乱数で生成し、パケットの先頭に平文で乗せる。
  受信側は「自分の持つ事前共有鍵 + 受信した ID」でテーブルを復元する。
  ID は見えても鍵が無ければテーブルは作れない。

この分割によりパケット仕様 `セッションID 4Byte + 文字順 2Byte + body 10Byte = 16Byte` に素直に乗る
（レイアウト詳細は後述）。

### 判断2: 文字セットは全角・清音のみに絞り、サイズを小さく保つ

**初版は濁音・半濁音・小書きを入れない**（"一旦ナシ"）。打てない語は出るが、アソビ枠なので
まず最小で回す。後から濁音ブロックを足せる（version を上げる前提）。

| 区分         | 数      | 中身                                    |
| ------------ | ------- | --------------------------------------- |
| ひらがな清音 | 46      | あ〜ん                                  |
| カタカナ清音 | 46      | ア〜ン                                  |
| 全角数字     | 10      | ０〜９                                  |
| 記号         | 19      | `　、。・！？「」（）…〜ー＆＠％＝＋／` |
| **合計**     | **121** |                                         |

制御コード（START/END）は**一旦保留**。終端・パディングは**不要**（判断5）。

各文字は **10 バイトのランダムコード**に符号化する（判断3）。文字種が 121 でも、
**1 文字 = body 10 バイトをまるごと使う**。

→ **1 パケット = 1 文字**。N 文字メッセージは N パケットに分かれ、順序は seq で復元する（判断6）。

長音符 `ー` はカタカナ語に必須なので記号に 1 つだけ残す。
文字セットの確定リスト（順序込み）は `electron/codec/alphabet.ts` で固定する。
**この順序が変わると既存 seed のテーブルも全部変わる**ので、確定後は安易にいじらない
（先頭にバージョン番号を持たせて管理）。

### 判断3: テーブルは「文字 → 10 バイトのランダムコード」割り当てで作る

```
for char of 文字セット:
  code = PRNG から 10 バイトの乱数      // 重複したら引き直す（80bit 空間なので実質起きない）
  charToCode[char] = code              // encode 用
  codeToChar[hex(code)] = char         // decode 用（完全一致の逆引き）

encode: 文字 → 10 バイトコード
decode: 10 バイトコード → 文字（hex で逆引き、無ければ未知）
```

- **なぜ 1 バイト換字でなく 10 バイト乱数か**: 1 文字 = 1 バイトの単純換字は鍵空間が小さく、
  頻度分析で簡単に破れる。10 バイト = 80bit の空間に 121 文字を散らせば、鍵（seed）なしの
  逆引きは事実上不可能。「共有者だけ復号」の強度が桁違いに上がる。
- 同じ seed → 同じ割り当てが再現される（決定的）。同じ文字は同一セッション内で常に同じコード。
- PRNG は外部依存なしの軽量決定的アルゴリズム（xmur3 で seed を 32bit 化 → mulberry32）を
  自前実装。ユーティリティ側でもレンダラー側でも同じ結果になるよう純 JS で書く。

> 注: 同一セッション内で同じ文字が同じコードになるため、長文では頻度分析の余地が残る。
> seq や位置を混ぜて 1 文字ごとに変える強化は次段階（今はスコープ外）。

### 判断4: 「テーブルを作る側」と「テーブルを使う側」を分離する（共有方式は後決め）

「何を共有するか」は **seed / 対応テーブル直接 / 鍵+salt** と迷いどころだが、これらは全部
**「テーブルをどう作るか」の差**でしかない。encode/decode は **テーブルさえあれば動く**ので、
2 つに分離しておけば共有方式の決定を後ろに倒せる。

```
Codec(table)                    ← encode/decode 本体。テーブルだけ受け取る（純粋・1 個で済む）
─────────────────────────────
tableFromSeed(seed)             ← seed 派
tableFromKeyAndSession(key, id) ← seed + salt 派（判断1 の 2 層 seed）
loadTable(blob)                 ← テーブル直接共有派
```

補足: 共有方式の本質は「毎回変える(salt)が欲しいか」。

- 毎回変えたい → seed 由来で常に導出（テーブルは保存しない）= `tableFromSeed` / `tableFromKeyAndSession`
- 固定テーブルで十分（同じ文 → 同じコードで可） → `loadTable` が最シンプル（PRNG 不要）

直接テーブルを共有しても salt を足したくなれば結局 `(table, id) → table'` の導出ステップが要り、
seed 方式に収束する。なので salt が欲しいなら最初から seed 派でよい。

**今回のスコープ**: コア `Codec(table)`（encode/decode）＋ `tableFromSeed(seed)` の 1 本だけ作る。
`tableFromKeyAndSession` / `loadTable` は後から足す（コアは触らない）。

### 判断5: 終端・パディングは不要

**1 パケット = 1 文字**で、body 10 バイトは常にその 1 文字のコードでまるごと埋まる。
「端数」や「空き」が生じる余地がないので、終端マーカーもパディングも要らない。
（10 バイトに複数文字を詰める設計なら終端が要るが、その設計は採らない。）

### 判断6: 文字順(seq) を 2 バイト持つ

1 パケットが 1 文字しか運ばないので、N 文字メッセージは N パケットに分かれる。
BLE 広告は順序保証も到達保証もないため、各パケットに「**何文字目か**」を示す
**文字順(seq) を 2 バイト**持たせ、受信側がこれで**正しい順に再結合**する。

- **2 バイト = 0..65535**。1 メッセージあたり最大 65536 文字 → 実用上の上限は事実上なし。
- アーカイブのモックは seq を 1 バイト（0..255）にしていたが、255 文字で頭打ち。
  長文・将来の余裕を見て 2 バイトに拡張する。
- seq は**順序復元の鍵**として必須（単なる重複除去では足りない）。
  メッセージ境界（どこまでで 1 通か）・欠落検出・再送は次段階。

## パケットレイアウト（1 パケット = 1 文字、論理 16 バイト）

```
[0..3]    sessionId  (4B)  自然乱数。テーブル salt。平文で送る
[4..5]    seq        (2B)  文字順。何文字目かを示す再結合インデックス（big-endian）
[6..15]   body       (10B) その 1 文字の 10 バイトコード（まるごと使う・終端不要）
```

合計 16 バイト (4 + 2 + 10) = BLE 1 パケットで「自由に動かせる 16Byte」に一致。
1 パケットが 1 文字なので、N 文字メッセージは seq 0..N-1 の N パケットになる。
この 16 バイトの pack/unpack と BLE トランスポート（Service UUID 128bit）への載せ方は
[communication-design.md](./communication-design.md) が正典（上のレイアウトもそちらと一致させること）。

## 自然乱数のソース（**未決・要相談**）

セッションID(4Byte) の生成にだけ自然乱数が要る。候補：

| 案                        | 中身                        | 所感                                 |
| ------------------------- | --------------------------- | ------------------------------------ |
| `crypto.randomBytes(4)`   | OS の CSPRNG                | 堅実。4 バイトならこれで十分         |
| 時刻 + ノイズ             | `Date.now()` 等を混ぜる     | 軽いが衝突しやすい                   |
| **BLE RSSI を種に混ぜる** | 受信電波強度を entropy 源に | ガラパゴス感 MAX・アソビ枠的に映える |

> 現状の傾き: 実用は `crypto.randomBytes`、アソビ要素として RSSI を混ぜる折衷もあり。ここは要決定。
